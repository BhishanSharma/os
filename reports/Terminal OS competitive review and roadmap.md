# Terminal OS Must Harden Before It Scales

Measured on its actual code (HEAD `3c9f14b`, 7 November 2026), Terminal OS scores about **2.9 out of 10** across seventeen categories, against about **9.0 for Windows 11 26H2, 9.35 for macOS 27 and 8.9 for a current Linux desktop**, and **4.4–5.4 for the leading independent systems** (SerenityOS, Redox, Haiku R1/beta6 and Genode's Sculpt OS). That already equals ToaruOS, a solo project fifteen years in the making, after roughly one month of intense, heavily AI-assisted work that produced about 72,000 lines: its own UEFI loader, 16-core SMP, copy-on-write processes, an e2fsck-verified ext3 journal, NVMe/AHCI/xHCI drivers, WPA2 Wi-Fi, a GPU-accelerated compositor and a ported Ladybird browser. Its weakness is depth exactly where production systems invested most: the kernel never turns on the CPU's no-execute bit, `mprotect` silently does nothing, almost every system call runs under one big kernel lock, there is no page cache or IOAPIC support, real-hardware evidence covers one Acer laptop, CI runs no tests, and any program can drive a 1,665-line shell running in ring 0. The most valuable next work is also the cheapest: about **3–5 person-months of hardening and bug fixing** would lift security from 2 to about 4 and remove likely hangs and crashes before more users and code pile on. A seven-milestone roadmap (M0–M6) can then carry the system into the independent tier (5–6) in about three years; the auditors' estimates sum to 256–413 person-weeks, roughly 5–8 person-years of conventional effort before overlaps are removed. Matching Windows, macOS and Linux across the board is out of reach for a one-person project, since Linux 7.3 alone merged **18,765 commits from 3,021 developers in 63 days** ([LWN](https://lwn.net/Articles/1101143/)), so the realistic meaning of "toe to toe" is beating them on measurable claims inside a narrow niche: a lean, private, coherent desktop on a few certified Intel laptops.

The mainstream and peer scores are the researchers' judgements from 2026 release notes and reporting. A four-point gap is therefore meaningful, but a half-point gap is not. ### What the scorecard says
**The gap to the independent tier is broad, not deep.** Terminal OS trails the best peer by about 2 to 3.5 points in every category except C5 (6 points behind Genode's capability design). No single feature closes it. Its best relative standing is in process and POSIX breadth and in developer experience (both 4). Its worst is in accessibility, community and security.

**Code reading changed some README-based guesses.** An earlier estimate built from the README put networking at 5, because WPA2 Wi-Fi plus HTTPS already beats SerenityOS and Redox, which have no Wi-Fi at all. The code shows legacy 802.11a/g rates on one antenna chain, no IPv6, no UDP for programs and no TCP congestion control, which is a 3. Developer experience moved the other way, from 2 to 4, thanks to the app template, `.tapp` packaging and a modern GCC 15.2 cross-toolchain.

**The mainstream systems' own soft spots are where a newcomer can aim.** Windows' lowest scores are power (8), reliability (8) and performance (8). On identical 8 GB Dell XPS 13s, Windows used **85.2% of RAM after boot versus about 31% for Fedora**, and restarted in **61 s versus 27 s** ([It's FOSS](https://itsfoss.com/news/fedora-beats-windows-11/)). Measurable leanness is therefore a credible battleground for a small system.

## One month, 72,000 lines: what the code genuinely does well

### Breadth that peers took years to reach
The breadth is real and unusually fast. SerenityOS took about six months to reach its first semi-working GCC port and a full year before its own browser rendered a page ([SerenityOS](https://serenityos.org/happy/1st/)). Terminal OS has had GCC 15.2, mlibc 7.0 and libstdc++ (C++23) running against its kernel since mid-October 2026, plus a statically linked Ladybird with Skia, ICU and Rust crates ([TOOLCHAIN.md](../docs/TOOLCHAIN.md); [ladybird/build.sh](../toolchain/ladybird/build.sh)).

The process model is likewise broader than hobby kernels usually reach in years: fork with copy-on-write, exec, a `posix_spawn`-like call that can launch a program as another user, threads with FS-base TLS, physical-address futexes, process groups and sessions, pseudo-terminals with termios, local sockets with file-descriptor passing, Mach-style ports with a name service, and a dynamic `ld.so` with working `dlopen` ([process.c](../src/impl/x86_64/sys/process.c)). That is enough for **bash 5.2 with job control, Vim 9.1, curl, SQLite and Lua**.

**Hardware depth on one vendor's platform exceeds what the independent tier has.** SerenityOS still has no Wi-Fi and no GPU support ([SerenityOS docs](https://github.com/SerenityOS/serenity/blob/master/Documentation/BareMetalInstallation.md)), and Redox's first GPU driver, which only sets display modes, arrived after about ten years ([Redox](https://redox-os.org/news/this-month-251231/)). Terminal OS has a 2,152-line clean-room Intel Wi-Fi driver modelled on OpenBSD's iwx(4) that joins WPA2 networks ([iwlwifi.c](../src/impl/x86_64/drivers/iwlwifi.c)); ten OpenCL-C GPU kernels, compiled offline and **checked against the CPU at boot**, that draw the desktop's blur, shadows and fades on Intel Gen12 ([GPU.md](../docs/GPU.md)); and NVMe, AHCI and xHCI with MSI, USB hubs to five tiers, USB Ethernet (CDC-ECM) and an I2C precision touchpad with palm rejection ([xhci.c](../src/impl/x86_64/drivers/xhci.c); [i2c_hid.c](../src/impl/x86_64/drivers/i2c_hid.c)).

**Storage that survives a crash test.** The ext3 driver writes a real journal, replays it at mount, and is validated by e2fsck in host tests and in a QEMU test that crashes mid-commit ([ext2.c](../src/impl/x86_64/drivers/ext2.c); [ext2_host_test.c](../tests/ext2_host_test.c)).

### A compositor and design system with more polish than the peers
The window server composites shared-memory surfaces only where something changed (a damage list). It flips frames at vsync and paints with up to eight threads, one per core ([windowserver/main.c](../user/programs/windowserver/main.c)). Every app draws from one design-token system with light and dark themes, eight accents and contrast settings ([tokens.json](../design/tokens.json)). Offloading blur to the GPU goes beyond what SerenityOS's or Haiku's servers do.

### Honest engineering habits
There are **zero TODO/FIXME markers** in the source. Every shortcut is written down instead as a "Cut" in [ROADMAP.md](../docs/ROADMAP.md), which the kernel audit found to be the one document that matches the code. Testing is also better than at most young systems: 25 QEMU system tests drive real images through serial and the QEMU monitor, including GUI clicks, USB hub hot-plug, SATA, CDC-ECM and ext3 crash replay ([run_tests.py](../tests/qemu/run_tests.py)), and an `attack` program checks that ELF, sigreturn, trampoline, port and sandbox abuse are refused ([attack.c](../user/programs/attack.c)).

### Why the speed is also the main risk
**The multitasking, SMP and virtual-memory core is only about four weeks old.** After 27 commits in October 2025, the repository was silent for eleven months. Then 119 commits landed between 8 October and 7 November 2026, and **63 of the 146 commits carry a Claude co-author trailer**. The median commit changes 432 lines and the largest 34,675.

The kernel audit found a real two-cores-in-the-kernel race in the big lock that was fixed on the audit day itself (commit `deeb0fd`). That is the signature of code that has had little soak time.

Peers are reacting to exactly this style of development: Redox banned LLM-generated contributions in March 2026 ([Phoronix](https://www.phoronix.com/news/Redox-OS-March-2026)), Ladybird closed public pull requests over contribution quality in June 2026 ([Wikipedia](https://en.wikipedia.org/wiki/Ladybird_(web_browser))), and Phoronix greets the weekly "vibe-coded OS" with open scepticism ([Phoronix](https://www.phoronix.com/news/NULLos)). **Terminal OS's velocity is an asset only if testing and review keep pace, and today they do not.**

## Fix first: a dozen defects that silently undo the protections

The audits found real care in the code. Every hardware wait has a timeout, and an internal "attack test" commit hardened the ELF loader against wrap-around, closed a heap disclosure and sanitised `sigreturn` frames. They also found a more dangerous class of defect: places where the system *appears* protected and is not. The worst is that **no-execute protection is never switched on**. The 32-bit entry code sets EFER.LME but never EFER.NXE, and the AP trampoline does the same ([boot/main.asm](../src/impl/x86_64/boot/main.asm)); the page-table code has no NX flag at all ([paging.h](../src/intf/drivers/paging.h)); the kernel image is mapped writable and the direct map of all RAM is writable *and* executable ([paging.c](../src/impl/x86_64/drivers/paging.c)); and the ELF loader ignores PF_X and copies small programs into writable pages ([process.c](../src/impl/x86_64/sys/process.c)). On top of that, mlibc's `mprotect` returns success and does nothing ([sysdeps.cpp](../toolchain/mlibc/terminalos/generic/sysdeps.cpp)), so guard pages and JIT W^X flips silently never happen. A no-op that reports success is worse than an honest `ENOSYS`, because programs believe they are protected. The same pattern recurs: `sigprocmask` is a no-op, `kill(pid, 0)` always succeeds, `setitimer` and `alarm` are "accepted and never fire", and `O_RDWR` on an existing file quietly opens it read-only.

The second cluster turns the sandbox into a suggestion. **`kcommand` lets any program drive the 1,665-line kernel shell in its own context**, including `download <url>`, `ping` and `wifi`. Only `syscall_net.c` checks the sandbox's network permission, so a sandboxed app without `network = yes` can probably still fetch URLs ([shell.c](../src/impl/x86_64/sys/shell.c); [syscall_net.c](../src/impl/x86_64/sys/syscall_net.c)). Shared-memory and local-socket names live in one global namespace with no owner, mode or sandbox check. Any program can therefore map, shrink or unlink the window server's `ws.<id>` surfaces, and the server trusts a pid supplied by the client ([windowserver/main.c](../user/programs/windowserver/main.c)).

The third cluster threatens data. NVMe is registered with no flush callback, and USB storage never sends SYNCHRONIZE CACHE, so ext3's commit-time `dev_flush` is a no-op on exactly the media most people boot from ([nvme.c](../src/impl/x86_64/drivers/nvme.c); [disk.c](../src/impl/x86_64/drivers/disk.c)). That undercuts the readme's "never half way" journal promise on drives with volatile write caches. It is also backwards that **installing to an internal SSD yields a FAT32 root** with no owners, no journal and no crash-atomic FAT updates, so the "better" installed mode is the weaker one ([main.c](../src/impl/kernel/main.c); [install.c](../src/impl/x86_64/sys/install.c)).

|---|---|---|---|

The documentation needs the same honesty pass. ROADMAP.md matches the code, but [USERSPACE.md](../docs/USERSPACE.md) still describes 14 programs, no pipes, exec or floating point and a 256 KiB stack; [ARCHITECTURE.md](../docs/ARCHITECTURE.md) claims a 100 Hz PIT and a 1 GiB heap and its driver table omits about 25 drivers; the [readme](../readme.md) cites a 40 MiB RAM disk, 16 TCP connections and about 30 commands; and [KNOWN-ISSUES.md](../docs/KNOWN-ISSUES.md) says FAT32 cannot rename, which was fixed on 7 November. A one-week refresh fixes all of it. Static limits (at most 16 windows, 256 tasks including threads, 16 accounts, 6 mounts, 8 ARP entries and a TCP backlog of 4) also make denial of service easy, so making those tables dynamic is cheap insurance. Together, the fixes in this section come to the **3–5 person-months** quoted at the top, and each is cheaper now than after mlibc, Ladybird and third-party packages start depending on today's behaviour.

## Missing features, ranked by what they unlock

**Most of the missing kernel pieces matter less as features than as unlockers for everything above them.**

*Syscall path and time.* Every clock read traps through `int 0x80` and takes the big lock, because there is no SYSCALL/SYSRET entry, per-CPU GS area or vDSO. Programs cannot use AVX at all, because the kernel never enables XSAVE. Time is a 32-bit millisecond counter that wraps after about 49.7 days.

*mlibc gaps.* mlibc implements about 108 sysdeps and returns ENOSYS for the rest. The missing ones include the setuid family, `symlink`/`link`, `utimensat`, `statvfs`, `epoll`, `eventfd`, `timerfd`, `inotify` and POSIX ptys, which blocks sudo, rsync, make's timestamp logic, GLib, libuv and Node ([sysdeps.hpp](../toolchain/mlibc/terminalos/include/mlibc/sysdeps.hpp)).

*A priority order exists.* Measurement work on Linux binaries shows that any application needs about 40 syscalls, half of Debian/Ubuntu (weighted by popularity) needs 145, and 90% needs 202 ([Tsai et al.](https://www.cs.unc.edu/~porter/pubs/login-fall16.pdf)). That gives a data-driven order for filling the gaps.

*Scalability.* The next tier is per-CPU run queues with priorities, so the compositor and audio stop competing equally with CPU hogs. After that come per-address-space VM locks, a page cache that shares library pages (today every program gets a private copy of each `.so`), a buddy allocator, guarded kernel stacks and an OOM killer.

*Hardware.* The missing pieces start with an IOAPIC driver, since modern PCs route PCI INTx through the IOAPIC and legacy NICs are therefore polled from the 100 Hz tick. Next come a probe-and-bind driver framework with multiple instances and suspend hooks; support for every xHCI controller rather than just the first, because Type-C ports often sit on the CPU's own controller; virtio; Wi-Fi at HT/VHT/HE rates plus WPA3, which is mandatory for 6 GHz and Wi-Fi 7 ([Cisco](https://www.cisco.com/c/en/us/products/collateral/wireless/catalyst-9100ax-access-points/wpa3-dep-guide-og.html)); Bluetooth and microphones; and thermal zones, without which the OS today has no critical-temperature shutdown at all.

*Networking.* What is needed is IPv6; UDP for programs, without which ports cannot do their own DNS, NTP, QUIC or WebRTC; and TCP congestion control with window scaling. Without window scaling, throughput is capped near 64 KiB per round trip, roughly 5 Mbit/s at 100 ms. TLS 1.3 also requires moving beyond BearSSL, which stops at TLS 1.2.

## How to improve further: borrow interfaces, drivers and process

### Present a Linux-shaped interface
**Every independent system that runs mainstream applications in 2026 got there by impersonating an existing interface, not by writing apps natively.** Managarm runs KDE Plasma 6 "usable for daily use" and GNOME Web with YouTube. It got there through mlibc plus Linux-compatible `/proc`, `/sys`, epoll, timerfd and signalfd ([Managarm](https://managarm.org/2026/10/18/oct-update.html); [Managarm](https://managarm.org/2026/10/13/0-epiphany.html)). Astral, a one-person C kernel on the same mlibc route, reached X.org, GCC, Wine and Minecraft ([OSnews](https://www.osnews.com/story/145388/astral-is-a-hobby-operating-system-with-x-org-minecraft-and-now-wine/)).

Terminal OS already links mlibc against Linux ABI headers. So its cheapest path is to make kernel semantics match Linux behind those sysdeps, and to track progress with os-test, which already publishes per-OS POSIX scores: Redox 73%, Genode 57% ([Redox](https://doc.redox-os.org/test-results/os-test/os-test-20250922/); [Genode](https://genode.org/files/jws/os-test/20260820/html/index.html)). That also keeps a later Linux-binary personality possible at low cost.

### Speak Wayland, then add GPU 3D
The second lever is to teach the existing compositor the Wayland protocol. One protocol unlocks GTK, Qt, SDL, XWayland and Wine's Wayland driver. Graphics should start with Mesa's software rasterisers and only later add Gen12 hardware rendering, through a subset of the i915 driver interface rather than imported Linux DRM code. That avoids pulling GPLv2 code into an MIT kernel. Genode built an Intel Gen8 3D driver with Mesa in four months ([Genode](https://genode.org/documentation/release-notes/17.08)).

### Protect the Ladybird port
Ladybird is worth keeping, but it is a moving target. Its alpha was still unreleased in October 2026 ([PiunikaWeb](https://piunikaweb.com/2026/10/06/ladybird-browser-alpha-update/)), and the port pins no upstream commit. Pinning it and adding a load-a-page smoke test protects the project's most impressive asset.

### Add Windows apps through Wine
Windows compatibility should come through Wine, after Wayland. Haiku ran 7-Zip, Inkscape and Notepad++ within months once its POSIX layer was solid ([Phoronix](https://www.phoronix.com/news/Wine-On-Haiku-Starts-2022)). By contrast, ReactOS still exports only Windows Server 2003 APIs after 28 years ([ReactOS](https://reactos.org/project-news/reactos-0416-released/)).

### Reuse drivers selectively
Drivers should be borrowed with care. Keep the native Intel Wi-Fi driver and add HT/VHT/HE rates. Then port wpa_supplicant, which is BSD-licensed and built around a driver-wrapper interface, to get WPA3-SAE, PMF and 802.1X in one step ([wpa_supplicant](https://android.googlesource.com/platform/external/wpa_supplicant_8/+/73b889335132164fdb87c5d8ebccad1bd5620b33/wpa_supplicant/README)). Apache-2.0 NimBLE is a licence-safe Bluetooth LE host ([NimBLE](https://summit.riot-os.org/wp-content/uploads/sites/10/2018/09/1_1-Szymon-Janc-NimBLE.pdf)).

A general Linux-driver emulation layer is a trap for one person. FreeBSD's funded LinuxKPI wireless work still had MediaTek 11n/11ac in progress and a Realtek driver that "can cause a panic at times" at the end of 2025 ([FreeBSD](https://www.freebsd.org/status/report-2025-10-2025-12/lkpi-wireless/)). Haiku's narrower BSD network-driver layer is the better model, and it gives Haiku the best Wi-Fi coverage in the peer group ([Haiku](https://www.haiku-os.org/get-haiku/r1beta6/release-notes/)).

### Set hardware priorities by market share
Intel holds **71.1% of notebook CPU units** ([TechSpot](https://www.techspot.com/news/113569-amd-crosses-30-client-cpu-market-share-against.html)), so the right order is to deepen Intel support first (newer display generations, Wi-Fi rates, microphones that go through Intel's SOF audio DSP, and s2idle sleep) and add MediaTek Wi-Fi for AMD laptops second. ARM64 laptops should wait. TUXEDO abandoned its Snapdragon X1 Elite Linux laptop after more than 18 months ([Tom's Hardware](https://www.tomshardware.com/software/linux/snapdragon-x1-elite-linux-laptop-cancelled-due-to-performance-concerns-linux-pc-maker-says-qualcomm-is-less-suitable-for-linux-than-expected)), and Asahi made the M3 official only in September 2026, without GPU acceleration or sleep ([Phoronix](https://www.phoronix.com/news/Asahi-Linux-Official-M3)). What should not wait is an `arch/` boundary in the code: today x86 inline assembly and raw PTE masks sit in supposedly generic files. That boundary is cheap now and expensive later.

### Harden in the right order
Security should follow the Kernel Self-Protection Project checklist ([KSPP](https://kspp.github.io/Recommended_Settings)). Take the build-time items while they are cheap: NX and W^X, UMIP, a stack protector, guarded stacks, zeroing allocators, a single user-copy path and a single DMA API. Defer user shadow stacks, which took Linux from 2018 patches to a 6.6 merge ([Phoronix](https://www.phoronix.com/news/Intel-Shadow-Stack-Linux-6.6)). Give Ladybird's WebContent processes a pledge/unveil-style sandbox, because remote web content is the largest attack surface the system will have.

### Plan Secure Boot as a sequence
Secure Boot needs a staged plan. Since 26 June 2026, Microsoft returns third-party binaries signed only with its 2023 UEFI CA ([Microsoft](https://techcommunity.microsoft.com/t5/hardware-dev-center/signing-with-the-new-2023-microsoft-uefi-certificates-what/ba-p/4455787)). A signed shim requires a legal entity, HSM-held keys, reproducible builds, SBAT metadata, a kernel that enforces lockdown and a review queue of 2–3 months ([shim-review](https://github.com/rhboot/shim-review)), and Microsoft-signed UEFI images must also be NX-compatible ([Microsoft](https://learn.microsoft.com/windows-hardware/drivers/dashboard/file-signing-reqs)). The realistic sequence is user-enrolled keys now, a MOK chain through an existing signed shim next, and an own shim only once a legal entity and lockdown exist.

### Make quality visible
**Quality needs to become something outsiders can see**, because reviewers will assume an AI-assisted OS is fragile until shown otherwise. Most of what that takes is cheap or free: run the existing QEMU/OVMF suite on 1, 2 and 4 virtual CPUs in CI; build host libFuzzer harnesses for FAT32, ext3, TCP/DHCP/DNS, USB descriptors, `.tapp` and the image decoders, as SerenityOS does through its Lagom host build on OSS-Fuzz ([Lagom](https://git.rgbcu.be/RGBCube/serenity/raw/commit/da170997d5754880255e2527a861aed304ed76ee/Meta/Lagom/ReadMe.md)); add a kernel UBSan runtime, about one to two days of work; use Coverity Scan, which is free for open source ([Coverity](https://scan.coverity.com/)); add a lock-order checker before the big lock comes apart; and publish lmbench, fio and iperf3 comparisons against Linux on the same laptop ([lmbench](https://manpages.ubuntu.com/manpages/xenial/lmbench.8.html)).

### Grow beyond one maintainer
The project side matters as much as the code. Redox's monthly reports earn it near-monthly Phoronix coverage ([Phoronix](https://www.phoronix.com/news/Redox-OS-June-2026)); small NLnet/NGI Zero grants, such as the €26,500 for Redox's signals work, fund exactly this kind of kernel plumbing ([NLnet](https://nlnet.nl/project/RedoxOS-Signals/)); and ToaruOS archiving its GitHub repository on 26 October 2026 after fifteen mostly solo years ([GitHub](https://github.com/klange/toaruos)) shows the default fate of one-person systems.

## Seven milestones from hobby kernel to credible contender

The roadmap orders work by leverage and by what later work depends on, not by visibility. M0 and M1 come first because they are cheap and protect everything built afterwards. M2 fixes the ABI before ports multiply, because each new port written against today's semantics (fake `mprotect`, per-thread pids, whole-file writes) is code to revisit later. M3 dismantles the big lock before Ladybird's multi-process design and real workloads hit its ceiling. M4 and M5 overlap, because hardware and desktop work draw on different skills. M6 comes last because a signed shim needs lockdown and a legal entity. Package signing with simple Ed25519 keys should still start in M2, since signed-update schemes are much harder to retrofit once an unsigned channel exists ([TUF](https://theupdateframework.io/)).

The calendar windows assume full-time work at roughly the AI-assisted pace seen in October 2026, plus at least one more regular contributor by M4. At a conventional solo pace, roughly double them.

### What "toe to toe" can mean
Even after M6, matching Windows, macOS and Linux everywhere is not the target. The only new kernel to reach mainstream scale in this era, Huawei's HongMeng, took about ten years by its own account ([Yahoo Finance/SCMP](https://finance.yahoo.com/news/tech-war-huawei-sees-harmonyos-093000614.html)).

The achievable target is to win on measurable axes where the incumbents are weakest. On identical 8 GB laptops, Windows restarts in 61 seconds and uses 85.2% of RAM after boot ([It's FOSS](https://itsfoss.com/news/fedora-beats-windows-11/)). Microsoft itself admits File Explorer latency and Copilot clutter ([The Register](https://theregister.com/2026/03/23/windows_quality_commitment/)). Free consumer security updates for Windows 10 end in October 2027 ([Help Net Security](https://www.helpnetsecurity.com/2026/06/26/microsoft-windows-10-free-security-updates-esu-program/)).

A Terminal OS that, on a few certified Intel laptops, publishes reproducible numbers would compete there on equal terms. Targets worth publishing are boot to desktop in under ten seconds, idle memory under 1 GB, no telemetry or agents, and input-to-photon latency within one frame. Gaming, where Windows holds 93.7% of Steam users, enterprise fleets and professional creative software are niches it should not chase.

## Conclusion

Terminal OS's breadth is, for now, a liability as much as an asset. Every driver, port and app built on today's semantics also builds on today's assumptions: no execute protection, `mprotect` that lies, a big lock that "drivers need no locks" relies on, and files written whole at close. So the order of the next year's work matters more than its volume.

AI-assisted development has moved the scarce resource from writing code to proving it works. The 2026 field already sees a "vibe-coded" OS every week, and Redox bans LLM contributions outright. In that field, the differentiators any project can control are visible evidence: CI that runs the tests, fuzzers that run clean, an os-test percentage, power numbers measured on named laptops, and honest notes on how the code was written.

The window for cheap decisions is also short. ARM64 laptops and memory-safe code are on course to become table stakes by about 2030. Two choices made now keep both options open at little cost: an architecture boundary in the kernel, and writing new parsers and drivers in Rust.
